Этот документ — техническое задание для Codex на полное внедрение нового справочника регионов, городов и школ, перенос существующих пользователей, изменение регистрации и личного кабинета, обработку заявок на отсутствующие школы, ограничение выдачи дипломов и добавление баланса `coins`.

Работу выполнять по этапам. После каждого этапа запускать указанные проверки. Не переходить дальше при ошибке, несоответствии контрольных количеств, потере пользовательских данных или неоднозначной миграции.

### 3.2. `temporary/user_school.csv`

Формат:

- UTF-8 с BOM;
- разделитель `;`;
- заголовки `user_id;source_school_id;school_status`;
- 17 279 строк;

Для других ролей один только `class_grade = 0` не является основанием для этого статуса. Количество дошкольников определить по восстановленной БД и вывести в отчёте. Значение нельзя задавать вручную константой.

В последовательности `user_id` есть пропуски. Это допустимо только если таких строк действительно нет в таблице `users`. Импорт должен сравнить множества идентификаторов CSV и БД и остановиться при любом расхождении.

## 4. Зафиксированные архитектурные решения

1. Основная иерархия: `Region → City → School`.
2. Каждая сущность имеет собственный сгенерированный внутренний `id`.
3. Отдельное поле `unique_id` не создавать: первичный ключ `id` уже выполняет эту функцию.
4. `ni_schools.csv.id` является только `source_school_id` для импорта.
5. После связывания пользователей `source_school_id` не входит в публичную модель и API.
6. Служебную карту `source_school_id → schools.id` сохранить до проверки production-переноса. Удалять её только отдельным последующим этапом.
7. `users.city` не заменять на `users.city_id`: город пользователя однозначно определяется через выбранную школу.
8. В `users` хранить `region_id`, потому что регион нужен даже при отсутствии школы.
9. `users.school_id` является nullable-внешним ключом на новый справочник школ.
10. Состояние без школы представляется `school_id = NULL` и `school_status`, а не фиктивной строкой школы.
11. Выбранная школа должна принадлежать выбранному региону. Это обязательно проверяется сервером.
12. Регистрация ищет школы внутри выбранного региона. Город показывается в подсказке и автоматически получается из выбранной школы.
13. Адрес школы хранится в БД и доступен администратору, но не возвращается публичным поиском регистрации.
14. Пользователь не может напрямую изменять `school_status`, `coins` или групповые признаки школы.
15. Ручная заявка пользователя не создаёт автоматически запись в общих таблицах `regions`, `cities` и `schools`.
16. Новая школа появляется в справочнике только после решения администратора.
17. Строковые колонки `users.country`, `users.city`, `users.school` и прежнюю таблицу школ сохранить на переходный период для проверки и отката. Удалить их отдельной contract-миграцией после подтверждения production.

## 5. Целевая модель данных

### 5.1. Enum `SchoolStatus`

Добавить Python/PostgreSQL enum с явным именем типа `school_status_enum`:

```text
selected
missing
submission_pending
submission_rejected
not_required
```

Смысл:

- `selected` — пользователь связан с подтверждённой школой;
- `missing` — школа не выбрана, форма ещё не отправлена;
- `submission_pending` — форма добавления школы рассматривается;
- `submission_rejected` — заявка отклонена, пользователь может исправить и отправить снова;
- `not_required` — школа не требуется, например дошкольнику с `class_grade = 0`.

Индексы и ограничения:

```text

OR

`region_id` сначала оставить nullable для безопасного переноса. Новая регистрация всегда требует регион. После разрешения всех legacy-исключений можно отдельной миграцией сделать колонку `NOT NULL`.

## 6. Нормализация строк

Создать одну общую серверную функцию нормализации, используемую импортом и административными операциями:

1. Unicode NFKC.
2. `strip()`.
3. Схлопывание последовательностей пробелов.
4. Приведение к нижнему регистру через `casefold()`.
5. Нормализация `ё` → `е` только в поисковом/нормализованном поле; оригинальное отображаемое значение сохранять.

Не изменять оригинальные `name`, `short_name`, `full_name`, `address` кроме удаления внешних пробелов и нормализации очевидных переводов строк.

Отображаемое имя выбирать детерминированно: сначала вариант с `ё`, затем лексикографически; все школы из группы должны ссылаться на этот City. ## 7. Бизнес-правила

### 7.1. Матрица доступа

| `school_status` | Вход в кабинет | Новая попытка | Завершение уже начатой попытки | Диплом |
| --- | --- | --- | --- | --- |
| `selected` | Да | Да | Да | Да |
| `missing` | Да | Нет | Да | Нет |
| `submission_pending` | Да | Да | Да | Нет |
| `submission_rejected` | Да | Нет | Да | Нет |
| `not_required` | Да | Да | Да | Да |

Администратор может скачать диплом для диагностики. Ученик и учитель не могут получить диплом ученика, пока его статус запрещает выдачу.

Проверки выполнять на backend. Скрытие кнопки во frontend не является контролем доступа.

### 7.2. Регистрация с выбранной школой

1. Пользователь выбирает регион.
2. Вводит не менее двух символов школы.
3. Backend ищет подстроку в кратком и полном названии только среди активных школ выбранного региона.
4. Frontend показывает краткое/полное название и город.
5. Пользователь выбирает конкретный объект, frontend сохраняет `school_id`.
6. Backend проверяет существование, активность и принадлежность школы региону.
7. Пользователь создаётся с `school_status = selected`.
8. Город берётся из `school.city`; свободный текст города не принимается.

### 7.3. Школа не найдена

1. Пользователь выбирает регион.
2. Ставит флажок «Моей школы нет в списке».
3. `school_id` должен быть `NULL`.
4. Пользователь создаётся со статусом `missing` и допускается в кабинет.
5. В кабинете постоянно показывается уведомление с кнопкой заполнения формы школы.
6. После отправки формы создаётся `school_submissions(status = pending)`, а пользователь получает `submission_pending`.
7. Пользователь со статусом `submission_pending` может участвовать в олимпиаде, но не может скачать диплом.
8. После одобрения пользователь связывается с существующей или новой школой и получает `selected`.
9. После отклонения получает `submission_rejected`, видит комментарий и может отправить исправленную заявку.

Не создавать запись школы автоматически при отправке формы.

### 7.4. Дошкольник

Если новый student выбирает `class_grade = 0`:

- регион обязателен;
- выбор школы скрывается или отключается;
- `school_id = NULL`;
- `school_status = not_required`;
- доступ к олимпиадам и дипломам полный.

Если существующий student с пустой школой имеет `class_grade = 0`, импорт преобразует `missing` в `not_required`. Для teacher/admin и других ролей это правило не применять автоматически.

Скрипт `manual_scripts/promote_student_grades.sh` должен учитывать переход `0 → 1`: при `school_status = not_required` после перевода в первый класс установить `school_status = missing`, сохранить `region_id`, оставить `school_id = NULL` и записать это в аудит. Иначе первоклассник навсегда сохранит дошкольное исключение.

### 7.5. Другой регион или другая страна

В списке регионов использовать системную запись `is_other = true`, а не специальный числовой идентификатор.

При её выборе:

- школа не выбирается из российского каталога;
- пользователь регистрируется как `missing`;
- в заявке обязательны фактические страна, регион, город и название школы;
- администратор при одобрении либо связывает заявку с существующими объектами, либо создаёт Region → City → School;
- после одобрения `users.region_id` заменяется на фактический регион.

### 7.6. Изменение профиля

- Пользователь и учитель, редактирующий ученика, передают только `region_id`, `school_id` и флажок отсутствующей школы.
- При смене региона выбранная школа очищается.
- Свободное редактирование строковых города и школы запрещается.
- При выборе новой подтверждённой школы статус становится `selected`.
- При отказе от выбора школы статус становится `missing`, кроме student с `class_grade = 0`.
- Нельзя передать `submission_pending`, `submission_rejected` или `not_required` напрямую из клиента.
- Администратор может корректировать связь, но backend всё равно проверяет регион школы и пишет аудит.

    "name": "Санкт-Петербург",
    "country_code": "RU",
    "is_other": false

```

Возвращать только активные регионы. Пустой запрос может вернуть весь список, так как регионов около 89. Системную запись `is_other = true` показывать последней.

### 8.2. Публичный поиск школ

```http
GET /api/v1/lookup/schools?region_id=1&query=лицей&limit=50
```

Ответ:

```json
[
  {
    "id": 123,
    "short_name": "Лицей № 1",
    "full_name": "ГБОУ Лицей № 1",
    "city": "Санкт-Петербург"
  }
]
```

Правила:

- `region_id` обязателен;
- `query` после trim — минимум 2, максимум 255 символов;
- поиск по вхождению подстроки;
- `limit` по умолчанию 20, максимум 50;
- сортировка: точные/начальные совпадения выше, затем `short_name`, `city`, `id`;
- только активные region/city/school;
- ответ не содержит `address`, `email`, `url`, `curator`, `info`, групповые признаки и `source_school_id`.

Старый `/lookup/cities` после переключения frontend удалить либо временно оставить как deprecated, но новый интерфейс регистрации его не использует.

- смена региона очищает несовместимую школу;
- VK-пользователь без географии получает безопасное незавершённое состояние и не получает фиктивную школу «Неизвестно».

### 13.5. Заявки

- создание pending-заявки;
- запрет второй pending-заявки;
- approval к существующей школе;
- approval с созданием новой школы;
- rejection с обязательным комментарием;
- корректные переходы пользователя;
- конкурентная повторная обработка не создаёт две школы;
- не-admin не может читать и обрабатывать административные заявки.

### 13.6. Олимпиада и диплом

- `selected`, `submission_pending`, `not_required` могут начать попытку;
- `missing`, `submission_rejected` не могут начать новую попытку;
- уже начатая попытка может быть продолжена;
- pending-пользователь не скачивает диплом прямым URL;
- учитель не скачивает такой диплом ученика;
- после approval ранее завершённая попытка становится доступной для диплома;
- admin-доступ для диагностики сохранён.

## 15. Итоговые SQL-проверки данных

Адаптировать имена enum при необходимости, но смысл проверок сохранить.

```sql
SELECT COUNT(*) FROM regions WHERE is_other = false;
-- ожидается 89 импортированных регионов

SELECT COUNT(*) FROM cities;
-- ожидается 29171 канонический город;
-- 29266 точных исходных пар сводятся к ним через нормализацию е/ё

SELECT COUNT(*) FROM schools;
-- ожидается 54517 импортированных школ

SELECT COUNT(*)
FROM users u
LEFT JOIN regions r ON r.id = u.region_id
WHERE u.region_id IS NOT NULL AND r.id IS NULL;
-- ожидается 0

SELECT COUNT(*)
FROM users u
LEFT JOIN schools s ON s.id = u.school_id
WHERE u.school_id IS NOT NULL AND s.id IS NULL;
-- ожидается 0

SELECT COUNT(*)
FROM users u
JOIN schools s ON s.id = u.school_id
JOIN cities c ON c.id = s.city_id
WHERE u.region_id IS DISTINCT FROM c.region_id;
-- ожидается 0

SELECT COUNT(*)
FROM users
WHERE (school_status = 'selected' AND school_id IS NULL)
   OR (school_status <> 'selected' AND school_id IS NOT NULL);
-- ожидается 0

SELECT COUNT(*) FROM users WHERE coins < 0;
-- ожидается 0

SELECT school_id, COUNT(*)
FROM users
WHERE school_id IS NOT NULL
GROUP BY school_id
ORDER BY COUNT(*) DESC
LIMIT 20;
-- контроль распределения, без ожидаемой фиксированной суммы по отдельной школе
```

Дополнительно сравнить до/после:

- число пользователей по ролям;
- число активных пользователей;
- число попыток и ответов;
- число связей teacher-student;
- распределение `school_status`;
- число пользователей без региона;
- число пользователей без школы по статусам;
- число школ по каждому групповому признаку.
