# Инструкция агенту: устранение проблем из `report_security.md`

## Цель

Последовательно устранить оставшиеся проблемы безопасности из `report_security.md`, не нарушив бизнес-логику олимпиады, доступ к восстановленным локальным данным и работу production-сборки.

Проблемы №1 и №2 пользователь считает устранёнными. Не переделывать их без необходимости, но в финальной проверке убедиться, что исправления не регрессировали.

## Обязательные ограничения

1. Работать только в `/Users/alexfedosov/Documents/ni_site_v2` и только в ветке `codex/v2-development`.
2. Перед изменениями выполнить `git branch --show-current`. Если активна другая ветка — остановиться и сообщить пользователю.
3. Соблюдать `AGENTS.md` и `codex.md`.
4. Не выполнять автоматически `git pull`, `git fetch`, `git push`, создание или слияние Pull Request.
5. Не переключаться на `main`, не делать merge/rebase/cherry-pick в `main`.
6. Не создавать commit без отдельной явной просьбы пользователя.
7. Не использовать `git reset --hard`, `git checkout --`, `docker compose down -v` и другие команды, способные уничтожить рабочие изменения, PostgreSQL или MinIO.
8. Рабочее дерево может содержать изменения пользователя. Перед каждым этапом проверить относящийся к нему diff и не перезаписывать посторонние изменения.

10. Не обращаться к production и не менять внешние credentials без отдельного разрешения пользователя.

## Порядок исправления

### Этап 1. Finding 3 — приватность дипломов и сертификатов

Проблема: `minio_init` включает анонимное чтение всего bucket `ni-site`; приватные документы имеют предсказуемые ключи, поэтому API-авторизация обходится прямым запросом к хранилищу.

Security-инвариант: диплом или сертификат нельзя получить без успешной проверки пользователя в API; знание object key не даёт доступ к приватному файлу.

Требования:

- удалить `mc anonymous set download local/ni-site` из production и local Compose;
- не возвращать постоянный публичный URL для дипломов и сертификатов;
- после проверки прав выдавать короткоживущий presigned GET либо проксировать файл через API;
- публичные материалы, если они действительно нужны без авторизации, отделить от приватных отдельным bucket/prefix с явной политикой;
- не ломать показ изображений заданий и опубликованного контента: сначала проследить все вызовы `public_url_for_key`, `presign_get` и frontend-потребителей;
- использовать непрогнозируемые object keys для новых приватных документов, если это совместимо с существующей моделью; старые ключи считать приватными независимо от формата.

Тесты и приёмка:

- анонимный запрос к приватному объекту получает отказ;
- студент не получает чужой диплом;
- учитель получает только разрешённые документы учеников;
- учитель получает только собственные сертификаты;
- администраторский сценарий остаётся работоспособным;
- после пересоздания `minio_init` bucket не становится публичным.

### Этап 2. Finding 4 — stored XSS через Markdown-ссылки

Проблема: самописный Markdown-рендерер блокирует только точное начало `javascript:` и вставляет HTML через `dangerouslySetInnerHTML`; управляющие символы и другие опасные схемы могут обойти проверку.

Security-инвариант: пользовательский Markdown не может создать исполняемый HTML или URL с опасной схемой после нормализации браузером.

Требования:

- заменить ручную обработку ссылок на поддерживаемый Markdown-парсер и sanitizer либо применить строгую централизованную санацию результата;
- разрешить только относительные URL и явно необходимые схемы `https:`/`http:`; решение по `mailto:` принять явно;
- удалить C0-управляющие символы до проверки URL;
- запретить `javascript:`, `data:`, `vbscript:` и неизвестные схемы независимо от регистра и вставленных tab/newline;
- не разрешать raw HTML;
- сохранить `rel="noopener noreferrer"` для внешних ссылок;
- добавить CSP как дополнительную защиту, не считая её заменой sanitizer;
- найти и унифицировать все Markdown-рендереры приложения.

Тесты и приёмка:

- безопасные ссылки и базовая разметка отображаются;
- payload с `javascript:`, смешанным регистром, tab/newline, HTML entities и `data:` не создаёт кликабельный опасный URL;
- HTML-теги и обработчики событий остаются текстом;
- тест проверяет итоговый DOM, а не только строковый regex.

### Этап 3. Finding 7 — полномочия модератора над банком заданий

Проблема: модератор может читать, изменять и удалять любые задания, включая чужие задания и задания опубликованных/завершённых олимпиад.

Security-инвариант: модератор создаёт и редактирует только разрешённые ему черновики; целостность опубликованных и уже оценённых олимпиад не зависит от последующих изменений банка заданий.

Требования:

- администратор сохраняет полный доступ;
- модератор видит и изменяет только собственные задания, если пользователь не утвердит более строгую модель;
- модератор не может менять или удалять задание, связанное с опубликованной, активной или завершённой олимпиадой;
- проверки выполнять на backend для list/get/update/delete, а не только скрывать кнопки;
- исключить TOCTOU: проверка и изменение должны выполняться в одной транзакционной границе;
- определить стратегию неизменности оценивания: версия/snapshot задания предпочтительнее зависимости попытки от изменяемой записи банка;
- аудитировать разрешённые и отклонённые критические изменения.

Тесты и приёмка:

- модератор создаёт задание и редактирует собственный разрешённый черновик;
- не может прочитать/изменить/удалить чужое задание;
- не может изменить связанное опубликованное задание;
- администратор сохраняет предусмотренный доступ;
- изменение банка не меняет уже сохранённые результаты и максимальные баллы.

Если внедрение snapshot/versioning требует изменения модели БД, сначала показать пользователю проект миграции и стратегию обратной совместимости.

### Этап 4. Finding 5 — OTP при назначении роли admin

Проблема: необходимость OTP определяется текущей ролью target-пользователя; повышение student/teacher до admin проходит без step-up.

Security-инвариант: любое изменение, которое создаёт, изменяет, отключает или лишает административной учётной записи полномочий, требует super-admin и свежий одноразовый OTP, связанный с actor, target, целью и временем.

Требования:

- принимать решение по переходу `old_role → requested_role`, а не только по старой роли;
- требовать OTP для назначения admin, снятия admin и изменения `is_active` администратора;
- ограничить операцию настроенным super-admin;
- OTP должен быть одноразовым, короткоживущим и purpose/target-bound;
- обеспечить транзакционную проверку инварианта единственного super-admin;
- service token не должен обходить правило без явно документированного узкого назначения;
- не возвращать секретные значения в API-ответах или аудит-логах.

Тесты и приёмка:

- обычный admin без OTP не повышает teacher/student до admin;
- неверный, просроченный или предназначенный другому target OTP отклоняется;
- корректный super-admin OTP используется ровно один раз;
- параллельные запросы не создают несколько super-admin;
- существующие безопасные изменения профиля не требуют OTP без причины.

### Этап 5. Finding 6 — tracked credentials

Проблема: `maintest.md` удалён, но отслеживаемый `backend/.env` всё ещё содержит непустые secret-like значения, включая administrator password.

Security-инвариант: Git-репозиторий и создаваемые из него артефакты не содержат действующих credentials или персональных секретов.

Требования:

- не показывать значения secrets;
- проверить `git ls-files` для `.env`-файлов и удалить реальные env-файлы из индекса, сохранив только безопасный `.env.example` с фиктивными значениями;
- добавить точные правила `.gitignore` для env, дампов, приватных ключей и локальных credentials;
- просканировать tracked-историю на имена/типы обнаруженных секретов без вывода значений;
- подготовить пользователю перечень credentials, которые требуется сменить, и перечень сессий, которые следует отозвать;
- не выполнять ротацию, отключение tunnel, переписывание Git-истории или force push автоматически;
- удаление секрета из текущего файла не считать достаточным, если он присутствует в истории.

Тесты и приёмка:

- `git ls-files` не показывает реальные `.env`;
- `.env.example` не содержит пригодных для входа значений;
- локальный запуск продолжает использовать игнорируемый `.env.local`;
- пользователь получил отдельный план ротации и очистки истории;
- finding закрывать только после подтверждения ротации пользователем.

### Этап 6. Finding 11 — отзыв refresh-токенов после смены пароля

Проблема: password-change меняет hash, но оставляет ранее выпущенные refresh-токены действующими.

Security-инвариант: после успешной смены или сброса пароля ни одна ранее выданная refresh-сессия не может получить новый access token.

Требования:

- в той же транзакции отозвать все refresh-токены пользователя;
- проверить также admin temporary-password и password-reset пути;
- при необходимости ввести `session_version`/`password_version`, включать его в JWT и проверять при refresh;
- решение о сохранении текущего устройства принять явно; безопасный default — отозвать все сессии и потребовать повторный вход;
- аудитировать смену пароля без записи пароля или токена.

Тесты и приёмка:

- refresh-токен, выпущенный до смены/сброса пароля, отклоняется;
- новый вход после смены создаёт рабочую сессию;
- logout и token rotation продолжают работать;
- операция смены пароля и отзыв токенов не могут частично разойтись при ошибке.

### Этап 7. Finding 12 — stored SSRF в PDF export

Проблема: `image_key` принимает произвольный HTTP(S)-URL, а PDF-генератор делает серверный `urlopen` без проверки адреса, redirect и размера ответа.

Security-инвариант: создание PDF не инициирует произвольные сетевые запросы; изображения читаются только из контролируемого object storage.

Требования:

- определить `image_key` как канонический object-store key, а не URL;
- валидировать допустимые prefix, длину и символы на create/update;
- получать изображение через storage client, не через произвольный URL;
- решить миграцию уже сохранённых URL до включения строгой валидации;
- ограничить размер загружаемых bytes, время операции и допустимые типы изображений;
- если remote URL является обязательным продуктовым требованием, остановиться и согласовать отдельный hardened fetcher: allowlist, DNS/IP validation, блокировка loopback/private/link-local, повторная проверка каждого redirect, лимиты и запрет credentials.

Тесты и приёмка:

- `http://127.0.0.1`, private/link-local адреса и redirect к ним не запрашиваются;
- обычный MinIO key корректно попадает в PDF;
- слишком большой или некорректный файл безопасно отклоняется;
- сетевой сбой не зависает и не раскрывает внутренние данные.

### Этап 8. Finding 9 — неограниченный legacy presigned PUT

Проблема: endpoint `/uploads/presign` выдаёт PUT URL без ограничения размера, хотя `/presign-post` уже поддерживает `content-length-range`.

Security-инвариант: каждая загрузка имеет серверно обеспеченный предел размера и разрешённый content type.

Требования:

- найти все frontend/API-клиенты legacy PUT;
- мигрировать их на bounded POST;
- после миграции удалить или окончательно отключить PUT endpoint;
- не доверять только заявленному MIME: проверять фактический тип после загрузки до публикации;
- добавить per-user quota/rate limit и lifecycle cleanup для сиротских объектов;
- возвращать структурированные ошибки API.

Тесты и приёмка:

- загрузка в пределах лимита работает;
- превышение лимита отклоняется самим storage policy;
- запрещённый MIME и неправильный prefix отклоняются;
- старый endpoint больше не выдаёт безлимитный URL;
- существующие формы admin/moderator используют новый путь.

### Этап 9. Finding 10 — CSV formula injection

Проблема: CSV quoting защищает структуру CSV, но не запрещает spreadsheet formulas из пользовательских полей и audit User-Agent/path.

Security-инвариант: экспортированная пользовательская строка всегда открывается как текст и не интерпретируется таблицей как формула.

Требования:

- реализовать одинаковую функцию spreadsheet-cell sanitization в backend и frontend либо перенести экспорт на одну серверную реализацию;
- до CSV quoting нейтрализовать значения, первый значимый символ которых `=`, `+`, `-`, `@`, tab или carriage return;
- не повредить числовые системные поля, которые генерирует приложение;
- применить защиту ко всем CSV-экспортам, не только к двум указанным в отчёте;
- документировать выбранный способ, например безопасный текстовый prefix.

Тесты и приёмка:

- payload для Excel/LibreOffice остаётся текстом;
- кавычки, запятые, CRLF и Unicode корректно экспортируются;
- обычные значения не искажаются;
- backend и frontend используют одинаковый набор опасных префиксов.

### Этап 10. Finding 8 — раскрытие `is_correct` студенту

Проблема: student attempt response возвращает `is_correct` после `results_released`, хотя доменное правило запрещает показывать правильность отдельных заданий.

Security-инвариант: студент никогда не получает per-task correctness или правильный ответ независимо от состояния публикации результатов.

Требования:

- удалить `is_correct` из student response, а не возвращать `null`;
- использовать отдельные типизированные response schemas для student и teacher/admin;
- проверить вложенный `payload`, чтобы `correct_option_id`, `correct_option_ids`, `expected` и аналоги не утекали;
- обновить OpenAPI и frontend types/consumers;
- сохранить студенту общий балл, процент, время и собственные ответы в пределах продуктовых правил.

Тесты и приёмка:

- до и после `results_released` student JSON не содержит `is_correct` и правильных ответов;
- teacher/admin получает разрешённую детализацию через отдельный endpoint/schema;
- frontend кабинета студента продолжает работать.

### Этап 11. Finding 13 — email enumeration при password reset

Проблема: неизвестный email получает 404, а существующий — 200, что раскрывает регистрацию пользователя.

Security-инвариант: публичный ответ и наблюдаемое поведение reset-request не позволяют определить существование email.

Требования:

- всегда возвращать одинаковый HTTP status и одинаковое общее сообщение;
- отправлять письмо и создавать token только для существующего подходящего аккаунта;
- сохранить rate limit по IP и нормализованному email;
- не логировать различие на публичном уровне; внутреннюю метрику/аудит вести без лишних PII;
- минимизировать заметную разницу времени без искусственной длительной задержки и DoS-риска;
- обновить OpenAPI, убрав публичный 404 `USER_NOT_FOUND`.

Тесты и приёмка:

- существующий и отсутствующий email получают одинаковые status/body;
- для отсутствующего пользователя token не создаётся и письмо не ставится в очередь;
- rate limit действует для обоих случаев;
- тест не требует реальной отправки email.

## Финальная регрессия пунктов 1 и 2

Не считать работу законченной без проверки:

- администратор не может изменить пароль другого администратора без предусмотренного super-admin + purpose/target-bound OTP;
- operational CSV с PII не отслеживаются Git, не попадают в сборочный контекст и заменены синтетическими fixtures там, где тестам нужны данные;
- реальные credentials и PII не появляются в новых логах, fixtures или отчётах.

Если эти свойства не выполняются, сообщить о регрессии отдельно; не расширять текущий патч молча.

Сначала подтвердить, что команда направлена на локальную БД. Не применять миграции к production автоматически.

Не использовать автоматический `npm audit fix`; сначала представить пользователю предлагаемые изменения зависимостей.

## Финальная проверка и отчёт агента

Перед завершением:

1. Повторно проверить все findings 3–13 по исходному source → control → sink.
2. Проверить отсутствие новых обходных путей и одинаковых небезопасных реализаций в других файлах.
3. Запустить backend tests, frontend tests/build и локальный smoke test ролей.
4. Проверить `git diff --check` и представить `git diff --stat` без создания commit.
5. Не показывать полный diff файлов с secrets/PII.
6. Обновить `report_security.md` только если пользователь отдельно попросит; исходный отчёт считать evidence, а не рабочим чек-листом.

Итоговый ответ должен содержать:

- какие findings исправлены и какими security-инвариантами;
- какие тесты и сборки прошли;
- какие проверки не удалось выполнить;
- какие миграции или ручные production-действия требуются;
- остаточные риски и решения, ожидающие пользователя;
- подтверждение, что `pull`, `fetch`, `push`, Pull Request и commit не выполнялись.
