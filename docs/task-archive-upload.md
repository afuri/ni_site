# Пакетная загрузка заданий

Реализовано 3 октября 2026 года. Загрузчик доступен только администратору
в разделе «Задания». Результат — обычные задания банка с ID, назначенными
PostgreSQL. Постоянных блоков заданий и экрана истории загрузок нет.

## Работа администратора

1. Подготовить ZIP: один MD-файл в корне, связанные картинки в `images/`.
   Использовать формат из `temporary/task_2026/math_grade_1_pool.md` и
   `temporary/task_2026/task_input_instruction.md`. PDF и инструкции в ZIP
   не включать. Полей ID, баллов и решений в MD быть не должно.
2. Нажать «Загрузить архив» и выбрать ZIP. Сервер проверяет структуру,
   обрабатывает картинки и записывает их в bucket. На этом шаге задания
   в банк ещё не добавляются.
3. Последовательно просматривать условие, изображение и правильный ответ.
   «Сохранить и далее» фиксирует одно задание в БД и обновляет банк.
   «Пропустить» окончательно пропускает текущее задание в этом проходе.
   При ошибках входных данных сохранение недоступно.
4. При необходимости нажать «Отменить оставшуюся загрузку». Созданные
   задания остаются, необработанный остаток пропускается.
5. После последнего решения появляется отчёт: сколько сохранено и пропущено.
   Причины пропусков доступны в раскрывающемся списке. Нажать «Закрыть».

Валидатор не закрывается по Escape, клику на фон или крестику.
Обновление страницы в том же браузере восстанавливает текущий шаг;
ZIP передавать повторно не требуется. После потери ответа сервера
«Обновить состояние» показывает подтверждённый сервером прогресс.

Редактирования внутри валидатора нет. Пропущенные задания добавляются
позже через обычную ручную форму. Сценарий повторной загрузки ZIP для
добавления пропусков не предусмотрен. Постоянной проверки дубликатов
между разными архивами нет: не загружайте один пакет как новую загрузку
повторно. Повторы запросов в рамках текущего просмотра не создают дублей.

## Формат и изображения

Контракт `format_version: 1` предусматривает четыре варианта олимпиады.
Каждая позиция бывает общей (`3`), разделённой на две пары (`5ab`, `5cd`)
либо на четыре версии (`1a`…`1d`). `task_count` задаёт число позиций,
а не число отдельных записей. Текущий пример содержит 8 позиций и 25 записей.

Парсер проверяет все индексы, обязательные поля, типы ответов и ссылки на
картинки. Неверная структура пакета отклоняет ZIP целиком. Ошибка отдельного
ответа или картинки блокирует только соответствующее задание.
Служебные файлы macOS игнорируются. Старый отдельный раздел `### Решение`
отбрасывается и не передаётся в валидатор; решение, вставленное прямо
в условие, нужно исключить при подготовке MD.

Поддерживаются JPEG, PNG и WebP. `image_width_px` уменьшает широкую картинку
с сохранением пропорций; меньшая не увеличивается. `original` сохраняет
размер. Ориентация EXIF учитывается. Одинаковые обработанные картинки внутри
одной загрузки сохраняются один раз. Разные размеры создают разные версии.
Сохранённые изображения не перезаписываются последующими загрузками.

Ручная форма задания и загрузчик ZIP используют одну серверную функцию
`app.services.task_images.prepare_image` (Pillow). JPEG и WebP при уменьшении
сохраняются с качеством 90, PNG — без потерь; используется фильтр LANCZOS.
Проверяются содержимое файла, соответствие расширения формату, количество
пикселей и отсутствие анимации. Размер без уменьшения сохраняется вместе
с исходными байтами, если не требуется исправление ориентации EXIF.

Ручная форма отправляет файл и ширину через `POST /api/v1/uploads/task-image`.
Допуск — администратор или модератор; лимит файла — `STORAGE_MAX_UPLOAD_MB`
(по умолчанию 10 МиБ). До подтверждения записи в bucket сохранение задания
заблокировано. При сбое показывается ошибка и кнопка повтора; локальная
подмена загрузки картинкой из браузера больше не выполняется. Повтор одного
файла с той же шириной использует тот же ключ по хешу обработанных байтов.
Изменение ширины отменяет ожидание старого ответа, чтобы он не подменил
результат новой обработки. Уже существующие изображения сохраняют свои ключи.

Обработка и операции с bucket выполняются в отдельных потоках с общим
ограничением в две операции на процесс API. Canvas в браузере требует меньше
CPU и памяти сервера и позволяет передавать уже уменьшенный файл. Серверная
обработка требует передачи оригинала, зато даёт единые проверки и результат
для ручной формы и ZIP. Для редких административных загрузок выбран этот
вариант. Для унификации новая миграция БД не требуется.

## Развёртывание

Обновить backend, админ-панель, Celery worker и beat. Установить зависимости
из `backend/requirements.txt` и применить `alembic upgrade head` в окружении
целевой БД. Новая миграция `a8b3d5f7c901` создаёт служебную таблицу
`task_upload_sessions`; существующие задания не изменяет.

Bucket должен существовать, API нужны права записи, worker — просмотра
и удаления объектов. Для предпросмотра используется `STORAGE_PUBLIC_BASE_URL`,
если он задан; иначе — подписанная ссылка. Этот адрес должен открываться
из браузера. В локальном Docker внутренний адрес `minio:9000` недоступен
браузеру, поэтому используется публичный адрес `http://localhost:9000/ni-site`.

На reverse proxy разрешить ZIP до 50 МиБ с запасом на multipart и время
обработки не менее 120 секунд. Клиент загрузчика ждёт ответ до 120 секунд.
Например, для Nginx: `client_max_body_size 51m` и `proxy_read_timeout 120s`.
Обычные запросы админ-панели сохраняют прежний таймаут.

Проверить работу Celery beat и worker, принимающего очередь `maintenance`:
задача `maintenance.cleanup_task_uploads` очищает временное состояние.

| Переменная | Значение по умолчанию |
| --- | --- |
| `TASK_UPLOAD_MAX_MB` | 50 МиБ ZIP |
| `TASK_UPLOAD_UNPACKED_MAX_MB` | 200 МиБ распакованных данных |
| `TASK_UPLOAD_MAX_FILES` | 1000 записей ZIP |
| `TASK_UPLOAD_MAX_TASKS` | 500 заданий |
| `TASK_UPLOAD_MAX_IMAGE_PIXELS` | 20 000 000 пикселей |
| `TASK_UPLOAD_MAX_IMAGE_WIDTH` | 4096 px для заданной ширины |
| `TASK_UPLOAD_PREPARING_TTL_SEC` | 600 секунд подготовки |
| `TASK_UPLOAD_ACTIVE_TTL_SEC` | 604800 секунд просмотра (7 дней) |
| `TASK_UPLOAD_RESULT_TTL_SEC` | 86400 секунд хранения итога (1 день) |
| `TASK_UPLOAD_IMAGE_RETENTION_DAYS` | 30 дней до очистки неиспользуемых картинок |
| `TASK_UPLOAD_CLEANUP_INTERVAL_SEC` | 3600 секунд между запусками очистки |
| `STORAGE_MAX_UPLOAD_MB` | 10 МиБ для отдельного изображения ручной формы |

Исходный ZIP не сохраняется постоянно. Временная сессия содержит очищенные
данные и результаты действий, без бинарных картинок или решений. Завершённые
сессии удаляются по сроку. Изображения пропусков удаляются после указанного
срока только при отсутствии ссылок из заданий и активных сессий. Сохранённые
задания и используемые ими картинки остаются.

## Локальная проверка

Применение миграции проверено на пустой БД и существующей схеме PostgreSQL,
включая откат и повторное применение новой миграции. В отдельной локальной
тестовой БД проверен настоящий `math_grade_1_pool.zip`: подготовлено
25 заданий и 14 изображений в MinIO; до сохранения записей `Task` нет;
все 25 отдельных сохранений создают уникальные ID.

Проверены параллельные повторы сохранения, атомарность при ошибке до commit,
пропуски, отмена, восстановление просмотра, права доступа, истечение сессии,
сбой хранилища и очистка с сохранением используемых изображений.
Выполнены проверки интерфейса, TypeScript и сборка админ-панели.

Для общей обработки изображений проверено побайтовое совпадение результатов
ручной формы и ZIP для JPEG, PNG и WebP, уменьшение без увеличения маленьких
картинок, EXIF, повреждённые файлы, неверные ширины и права модератора.
Проверены сбой bucket с последующим повтором и блокировка сохранения формы,
а также игнорирование запоздавших ответов после изменения ширины или очистки.
В интеграционном тесте с настоящим MinIO подтверждено побайтовое совпадение
ручной загрузки и ZIP, повторное использование ключа и сохранение всех
25 заданий. В браузере вручную добавлено задание только в тестовую БД:
изображение имело фактический размер 400 × 247 px и настоящий ключ bucket.

Во встроенном браузере под тестовым `admin01` проверены загрузка реального
ZIP, отображение картинки, отдельное сохранение, пропуск и восстановление
третьего задания после обновления страницы. Отмена оставила одну запись
и 24 пропуска. На отдельном небольшом тестовом архиве проверены итоговое окно,
раскрытие причин пропусков и восстановление отчёта. Рабочая локальная БД
`ni_site` сохранила исходные 161 задание.

Backend-тесты используют `TEST_DATABASE_URL` и пересоздают таблицы:
запускать их только на отдельной тестовой БД. Для реального MinIO-теста
задаются `TEST_S3_ENDPOINT`, `TEST_S3_ACCESS_KEY`, `TEST_S3_SECRET_KEY`;
он использует собственный временный bucket. Рабочая локальная БД `ni_site`
при этих проверках не очищается.
