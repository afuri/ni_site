# Открытие диплома браузером

Новый и прежний личные кабинеты используют общий обработчик открытия диплома.
При нажатии кнопки он сразу открывает вкладку и показывает «Загрузка диплома…».
Затем общий API-клиент запрашивает ссылку, при необходимости обновляет истёкшую
сессию и повторяет запрос. После получения ссылки вкладка переходит на исходный
JPG, который загружает и показывает сам браузер.

Изображение больше не скачивается JavaScript целиком в Blob. Временный object URL
и его удаление через 120 секунд исключены. На компьютере остаётся обычное открытие
JPG в новой вкладке с возможностью сохранить или распечатать его средствами
браузера; на телефоне — сохранить или поделиться изображением средствами браузера.

## Контракт API

Авторизованный запрос:

```http
GET /api/v1/attempts/42/diploma?response_mode=json
Authorization: Bearer <access_token>
Accept: application/json
```

Ответ 200 с `Cache-Control: private, no-store`:

```json
{
  "url": "https://site.example/ni-site/attempt_42.jpg",
  "filename": "attempt_42.jpg"
}
```

Запрос без параметра или с `response_mode=redirect` сохраняет прежний ответ 307
с тем же адресом файла. Используются существующий публичный URL или прежний
механизм подписанной ссылки. Правила доступа не изменены: собственная попытка
ученика, подтверждённая связь для учителя, полный доступ администратора;
проверка подтверждения школы остаётся действующей.

JWT передаётся только API в заголовке авторизации; в URL файла он не включается.
Полученная ссылка проверяется на HTTP(S) и отсутствие встроенных имени/пароля.
Повторный запрос API после 401 выполняется общим клиентом. Таймаут каждого
сетевого запроса — 15 секунд; обновление сессии и повтор могут увеличить общее
ожидание. При ошибке получения ссылки сообщение остаётся во вкладке с кнопкой
закрытия и отображается в личном кабинете. При заблокированном окне запрос
ссылки не выполняется. Закрытую пользователем вкладку обработчик не открывает заново.

API, как и прежде, не проверяет наличие JPG в bucket и не передаёт изображение
через себя. Дополнительного HEAD-запроса к хранилищу нет. Ошибки после перехода
на JPG, например отсутствие файла или обрыв сети, обрабатывает сам браузер.
Успешная выдача ссылки не доказывает завершённое скачивание файла. В аудите
новый запрос имеет статус 200 вместо прежнего 307; путь события сохраняется.

## Применение

Сначала обновить API, затем собрать и опубликовать основное приложение обычным
способом. Обновлённый интерфейс требует поддержки `response_mode=json` на API.
Выпуск не требует миграции БД, новых библиотек, настроек bucket или повторной
загрузки дипломов. Изменений фоновых задач нет: worker и beat специально для
этого исправления пересобирать не требуется.

## Проверка после публикации

- В новом и прежнем кабинетах открыть диплом, проверить загрузочную надпись и
  переход на исходный JPG. В сети должен быть запрос JSON и загрузка JPG
  браузером, без запроса изображения через fetch и без адреса `blob:`.
- На ПК проверить сохранение и печать изображения. На Safari iOS и Chrome Android
  проверить открытие и сохранение/отправку изображения.
- С истёкшим access token проверить обновление сессии и успешное получение ссылки.
- Заблокировать всплывающие окна, отключить сеть при получении ссылки, закрыть
  вкладку до ответа — интерфейс должен объяснять отказ либо завершать ожидание
  без повторного открытия вкладки.
- Убедиться, что прямой старый авторизованный запрос по-прежнему возвращает 307,
  а чужая попытка и неподтверждённая школа не получают ссылку.

Локальные автопроверки покрывают оба режима API, права доступа, подписанный URL,
ошибки хранилища, OpenAPI, загрузочный экран, ошибки, блокировку/закрытие вкладки,
некорректные ссылки, обновление сессии, таймаут и кнопку прежнего кабинета.
Реальные мобильные устройства этими автопроверками не заменяются.

Локально успешно выполнены 25 проверок API и 59 проверок интерфейса/общего
клиента, включая существующий загрузчик PDF. Production-сборка основного
приложения успешна.
