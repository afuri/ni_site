# План пакетной загрузки заданий из ZIP

Дата: 3 октября 2026 года. Статус: реализовано и проверено локально.
Инструкция по использованию и настройкам: [task-archive-upload.md](task-archive-upload.md).

## 1. Назначение и границы

Загрузчик переносит задания из одного архива в существующий банк заданий.
Один MD описывает один класс и один предмет; архив является входным пакетом,
а не новой сущностью платформы. Результат работы — обычные записи `Task`
с назначенными сервером ID, видимые в разделе «Задания».

Постоянные блоки с собственными ID, история импортов, список загрузок,
фильтры по архиву и связи заданий с архивными блоками не нужны. Название
`pool_title` используется как описание текущего входного пакета в валидаторе.
Прогресс виден по созданным заданиям и счётчикам текущего окна.

Каждое задание сохраняется отдельно. Пропуск окончателен для текущего прохода;
затем задание можно создать вручную обычной формой. Однократность означает
один проход по принятому архиву, без сценария повторной загрузки для добавления
пропусков. Постоянный реестр отпечатков всех когда-либо загруженных ZIP
и сравнение заданий между архивами в эту реализацию не входят.

Доступ к загрузчику имеет только `admin`. Баллы задаются при привязке задания
к олимпиаде. Входной файл содержит условия, ответы и параметры изображений,
без платформенных ID, полей баллов и решений.

## 2. Подготовка PDF и контракт Markdown

При предварительной обработке PDF агент извлекает условия, правильные ответы
и ссылки на подготовленные изображения. Текст решений, пояснения и ход
вычислений отбрасываются и не попадают ни в MD, ни в отчёт обработки.

Если отдельной строки ответа нет, агент может извлечь итоговое значение
из заключения решения, не перенося само решение. Например, для `6ab`
из текущего PDF сохраняется только `expected: 5`.

Использовать текущий контракт `format_version: 1` из
`temporary/task_2026/math_grade_1_pool.md`. После `## Задание <индекс>`
находятся один YAML-блок и `### Условие`. Допустимые поля задания:
`title`, `task_type`, `image_file`, `image_width_px`, `image_position`, `payload`.

Разделы с решениями не являются частью формата. Для защиты от старых файлов
парсер распознаёт отдельный раздел `### Решение` и отбрасывает его текст
до следующего задания: без сохранения в черновик, передачи в API или показа
в валидаторе. Поля `solution` и аналогичные дополнительные поля не принимаются.
Парсер не может надёжно распознать решение, вставленное прямо в условие;
чистоту условий обеспечивает обработка PDF и просмотр администратором.

В корне ZIP находится один MD в UTF-8 и папка `images/`, если есть картинки.
Служебные файлы macOS (`.DS_Store`, `__MACOSX`, `._*`) игнорируются.
Исходный PDF, инструкция и отчёт обработки в пакет не включаются.

Проверки общего описания:

- предмет `math` или `cs`, класс 0–11, версия формата 1;
- непустые `pool_title` и `subject_label`, четыре варианта для текущего формата;
- `task_count` означает число позиций в каждом варианте;
- `split_tasks` содержит значения 2 или 4 для существующих позиций;
- индексы уникальны и соответствуют распределению `1a`…`1d`, `5ab`/`5cd`
  или общей позиции `3`; все четыре варианта покрывают 1…`task_count`;
- паттерн использует только `{subject_label}`, `{grade}`, `{number}`, `{index}`;
  сформированное название содержит 1–255 символов.

Проверки задания:

- допустимые поля и тип, непустое условие, заполненный ответ без заглушек;
- строгие типы числовых ответов, конечные числа и положительная погрешность;
- непустые варианты выбора, уникальные обозначения и допустимые правильные ответы;
- точный путь изображения, фактический формат, корректная ширина либо `original`;
- `image_position` равен `before` или `after` и преобразуется в
  `payload.image_position`, как в текущей ручной форме;
- безопасный YAML-загрузчик, запрет повторяющихся ключей;
- итоговые данные проходят `TaskCreate` и дополнительные строгие проверки
  входного контракта, которых пока нет в этой схеме.

Повреждённый ZIP, несколько MD, неверное общее описание и неоднозначные
индексы отклоняют весь пакет до его приёма. Ошибки отдельных ответов,
payload или картинок показываются рядом с соответствующим заданием;
такое задание можно только пропустить, а остальные обработать.

Чтение ZIP должно проверять пути, дубли, отсутствие символьных ссылок,
шифрования и выходов через `..`. Ограничить размер загрузки, распакованный
размер, количество файлов и число пикселей изображений через конфигурацию.

## 3. Работа администратора

1. В разделе «Задания» добавить кнопку «Загрузить архив».
2. После выбора ZIP показать подготовку: проверка MD, обработка изображений
   и загрузка в bucket. До открытия валидатора задания в `tasks` не создаются.
3. Открыть последовательный модальный валидатор с описанием пакета,
   индексом и прогрессом «Задание 7 из 25». Предпросмотр показывает условие,
   картинку в заданной позиции, варианты ответа и правильный ответ.
4. «Сохранить и далее» создаёт одно задание с отдельным commit в PostgreSQL.
   Перейти дальше только после подтверждения сервера. Созданное задание
   становится доступно в обычном банке, список обновляется после сохранения.
5. «Пропустить» переходит к следующему заданию без создания `Task`.
   Ошибки сохраняемого задания блокируют кнопку сохранения.
6. «Отменить оставшуюся загрузку» прекращает просмотр и открывает итоговое окно.
   Уже сохранённые задания остаются; остальные в текущем пакете пропускаются.
7. После последнего задания автоматически показать краткий итог:
   «Сохранено 20 из 25. Пропущено 5». Добавить индексы пропусков и их причины,
   включая ошибки и отмену оставшегося просмотра. ID отдельного блока нет.
8. «Закрыть» в итоговом окне возвращает к обновлённому банку заданий.

Валидатор не закрывается по фону, Escape или крестику. Штатный выход —
обработка последнего задания либо отмена оставшейся загрузки.
Обновление страницы восстанавливает только текущую временную сессию
без повторной передачи архива. Для этого браузер хранит её технический токен;
отдельный экран истории или выбора прежних импортов не создаётся.

## 4. Временная сессия и защита от двойного сохранения

Для работы валидатора требуется временное серверное состояние: очищенные
данные заданий, ключи подготовленных картинок, текущий индекс, результаты
сохранения и счётчики. Это техническая сессия загрузки, не постоянный блок.
Её токен используется только в запросах и не выводится пользователю.

Предлагается одна служебная таблица `task_upload_sessions`: уникальный токен
запроса, автор, состояние подготовки/просмотра/завершения, срок очистки,
черновик JSONB и результаты действий. В JSONB нет ZIP, картинок или решений.
Завершённые сессии удаляются после короткого срока для восстановления ответа
при сбое связи; сроки завершённых и незавершённых сессий задаются конфигурацией.
После очистки сохраняются только обычные задания и стандартный аудит их
создания, предусмотренный проектом. История импортов не накапливается.

Сохранение выполняется в одной транзакции:

1. Заблокировать строку сессии.
2. Если это задание уже сохранено, вернуть прежний `task_id` без новой записи.
3. Проверить состояние сессии, текущий индекс и готовность данных.
4. Создать `Task`, получить ID через `flush()`.
5. Зафиксировать ID и результат в сессии, добавить стандартный аудит.
6. Выполнить один commit; при ошибке откатить текущую операцию целиком.

Пропуск также фиксируется под блокировкой. Повтор того же действия возвращает
прежний результат; изменение уже принятого решения запрещено. После последнего
действия сессия закрывается. Повтор запроса после потери ответа или запрос
из второй вкладки не создаёт дубль задания и не перескакивает очередь.

Текущий `TasksRepo.create()` выполняет commit самостоятельно. Для импорта
нужен метод без внутреннего commit либо отдельный сервис, чтобы `Task`
и результат его сохранения фиксировались атомарно. Обычная ручная форма
сохраняет существующее поведение. Ошибка БД оставляет текущий индекс
необработанным и окно открытым, сохранив задания предыдущих шагов.

## 5. Изображения и очистка

До открытия валидатора корректные связанные картинки обрабатываются
и загружаются в bucket. Проверять JPEG/PNG/WebP по содержимому.
Широкую картинку уменьшать до заданной ширины с сохранением пропорций;
меньшую не увеличивать. `original` сохраняет исходный размер.

Одинаковый результат обработки общего исходника загружается один раз.
При разных требуемых размерах создаются отдельные версии. Ключи формируются
на сервере с уникальным префиксом этой загрузки и хешем обработанного файла,
например `tasks/imports/<random_prefix>/<image_hash>.jpg`.
Это служебные ключи хранения, не ID постоянного блока заданий.

Сохранение задания использует уже загруженный `image_key`. Картинка
сохранённого задания остаётся неизменной. Изображения пропусков остаются
временно; фоновая очистка удаляет только файлы, не используемые никакими
`Task.image_key` или активной сессией просмотра.

Предпросмотр получает ссылки через административный API сессии:
существующий `/uploads/{key}` требует наличие `Task` и для черновика не подходит.
Используется настроенный публичный адрес bucket, а при его отсутствии —
временная подписанная ссылка. Доступ ученика к картинкам через API сохраняет
существующие проверки.

Исходный ZIP читается в ограниченный буфер памяти и освобождается после
подготовки; постоянно на сервере не сохраняется. Синхронные операции boto3 и обработки изображений выполняются
в ограниченном пуле вне event loop. При сбое подготовки сервер сообщает
ошибку, без фиктивного успешного результата. После просмотра сервер удаляет
черновик по правилам очистки; итоговый отчёт не становится постоянной записью
в интерфейсе. Данные для отложенной очистки картинок не должны сохранять MD.

## 6. API и этапы реализации

Выделить роутер `/api/v1/admin/task-uploads` с доступом только `admin`.
Токен начального запроса генерируется клиентом и связывает операции одной
временной сессии. Повтор начального запроса с тем же токеном возвращает
его состояние, а не создаёт новую загрузку.

| Метод и путь | Назначение |
| --- | --- |
| `POST /admin/task-uploads` | Принять ZIP и токен запроса, подготовить временную сессию |
| `GET /admin/task-uploads/{token}` | Восстановить текущий просмотр и ссылки предпросмотра |
| `POST /admin/task-uploads/{token}/tasks/{index}/save` | Сохранить текущее задание, вернуть ID и следующий шаг |
| `POST /admin/task-uploads/{token}/tasks/{index}/skip` | Пропустить задание и вернуть следующий шаг |
| `POST /admin/task-uploads/{token}/cancel` | Закрыть оставшуюся очередь и вернуть итог |

Сохранение берёт данные из очищенного серверного черновика. Ответ последнего
шага содержит итоговые счётчики. Список старых загрузок, фильтр по архиву,
связь архива с олимпиадой и редактирование задания в валидаторе не требуются.
Запросы, ответы и структурированные ошибки описать в Pydantic и OpenAPI.

Этапы реализации:

1. Парсер ZIP/MD, безопасная валидация и отбрасывание решений;
   зависимости для YAML и изображений в production requirements.
2. Временная модель и миграция, транзакционное сохранение, пропуск и очистка.
3. Подготовка картинок, административные preview-ссылки и API сессии.
4. Кнопка загрузки, валидатор, итоговое окно и обновление банка заданий.
   У `Modal` добавить скрытие крестика с корректным начальным фокусом,
   сохранив поведение остальных окон.
5. Целевые backend/UI-проверки и краткая инструкция администратору.

## 7. Критерии готовности

- Текущий архив разбирается как 25 заданий, 14 исходных картинок и 8 позиций
  в каждом из четырёх вариантов. Общее задание `3` сохраняется один раз.
- До первого подтверждения в `tasks` не добавлено ни одного задания.
- «20 сохранить, 5 пропустить» создаёт ровно 20 обычных заданий и верный итог.
- Отмена оставляет уже созданные задания и прекращает оставшуюся очередь.
- Двойное нажатие, потеря ответа и две вкладки не создают дубли в одной сессии;
  сбой между `flush()` и commit не оставляет задания без результата операции.
- Обновление страницы восстанавливает текущий просмотр без передачи ZIP.
- Решения отсутствуют в генерируемом MD, черновике, API и валидаторе.
  Старый отдельный раздел решения отбрасывается до сохранения черновика.
- Предпросмотр соответствует сохранённому условию, ответу, позиции и ширине картинки.
- Очистка временных данных сохраняет все используемые заданиями изображения.
- Миграция проверена на чистой и текущей схеме PostgreSQL; выполнены целевые
  тесты парсера, транзакций и UI, typecheck и сборка админ-панели.
- Обычное ручное создание и просмотр банка заданий продолжают работать.
