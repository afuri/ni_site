# Изображения и аудит: исправления без миграции

Изменения подготовлены по диагностике 9 октября 2026. Все таблицы, типы полей и индексы остаются прежними. Alembic для этого выпуска запускать не требуется.

## Изображения

- Получение ссылок на картинки в админке использует общий механизм для списка заданий, предпросмотра олимпиады и просмотра попытки. Одновременно выполняются не более шести запросов ссылок во всех этих представлениях вместе в одной браузерной вкладке; одинаковые ключи в одном представлении исключаются.
- Временные ошибки сети, 429 и 5xx получают не более двух повторов. Retry-After учитывается, постоянные отказы доступа не повторяются. Повтор больше не вызывается бесконечно изменением состояния React.
- При смене страницы или закрытии представления отменяются выполняющиеся и ожидающие запросы. Успешные изображения показываются по мере получения ссылок; подписанные URL обновляются до истечения срока, пока представление открыто.
- S3-проверка и формирование ссылок выполняются вне цикла асинхронной обработки API, не более четырёх работ на процесс. Проверка внешних зависимостей health/deps использует тот же механизм.
- Клиент S3 переиспользуется внутри процесса; первая проверка endpoint выполняется единожды при успешной инициализации. В Celery после fork клиент и блокировка создаются заново. Неудачная инициализация имеет паузу пять секунд, затем может восстановиться. Пробные клиенты закрываются.
- Для S3 явно заданы connect_timeout=2 секунды, read_timeout=5 секунд; проверка endpoint имеет одну попытку, обычные операции — максимум две. Настройки доступа к bucket и существующий выбор endpoint сохраняются.
- Обработчик чтения ссылки завершает свою read-only транзакцию до обращения к хранилищу, освобождая соединение PostgreSQL.
- Таймаут/операционный отказ БД при авторизации или проверке доступа к файлу возвращает HTTP 503 с кодом database_unavailable. Проверки авторизации и доступности задания сохраняются; доступ к закрытой задаче не выдаётся при отказе БД. OpenAPI дополнен примером ошибки.
- Медленные storage-операции записывают storage_work_slow operation=... elapsed_ms=..., а временная недоступность БД при выдаче ссылки — upload_database_unavailable reason=.... Эти записи не содержат ключей доступа, адресов email, токенов или SQL.

Диагностика доказала таймаут установки соединений PostgreSQL, но не установила исходную причину задержки. Исправления устраняют обнаруженное блокирование асинхронной обработки и неограниченные всплески/повторы. Эффект на сервере необходимо проверить после выпуска, включая первое открытие большой страницы заданий после перезапуска.

## Аудит

Записи audit_logs, создаваемые через db.add или изменением ORM-объекта, перед INSERT/UPDATE приводятся к существующим ограничениям колонок. Для path и user_agent это 255 символов; также соблюдаются длины action, method, ip и request_id. Нулевые символы удаляются.

При усечении сохраняется начало строки. В существующем JSONB details добавляется audit_field_normalization с именами изменённых полей, исходной/сохранённой длиной, флагом усечения и количеством удалённых нулевых символов. Остальные details сохраняются. Полное длинное значение в JSON не переносится. Таким образом, событие сохраняется, но превышающая лимит часть строки теряется — это ограничение выбранного решения без миграции.

Обработка выполняется общим ORM-событием, поэтому действует как для HTTP-аудита, так и для бизнес-событий. Прямой SQL и bulk INSERT/UPDATE через session.execute этой обработкой не покрываются. Убрано лишнее чтение записи после успешной записи HTTP-аудита: идентификатор уже получен при INSERT, остальные значения переданы вызывающим кодом.

## Удаление аккаунтов

Очистка аккаунтов не изменена. Поиск аудита по JSON-полям всё ещё может требовать просмотра таблицы. Подтверждённое ускорение этого поиска требует проверки плана и добавления индексов; данная работа отложена по условию выпуска без миграции. Объём удаляемых связанных данных не сокращается.

## Применение на сервере

После получения обновлённого кода, в сервисное окно:

```bash
cd /opt/ni_site
docker compose build api worker beat
docker compose up -d --no-deps --force-recreate api worker beat
```

Общий код хранилища используется также фоновыми задачами, поэтому API, worker и beat должны запускаться с согласованной версией. Параметры 6 API / 4 Celery, PostgreSQL и Redis менять не требуется.

Собрать админку и опубликовать её статику существующим способом из deploy.md:

```bash
cd /opt/ni_site/frontend
npm ci
npm run build:admin
```

Путь публикации Nginx зависит от текущей конфигурации сервера. Новых переменных окружения и новых библиотек эти изменения не требуют.

## Проверки

Регрессионные проверки охватывают ограничение параллельных запросов между представлениями, отсутствие бесконечных повторов, Retry-After, отмену устаревших запросов, обновление подписанных URL, освобождение БД перед S3, доступ к изображениям, восстановление после отказа S3 и запись длинных Unicode-полей аудита в прежние varchar-колонки.

Тестирование БД выполняется на отдельных временных PostgreSQL/Redis. Работающий сервер и рабочая база не изменяются. Реальная отправка писем и обращения к рабочему хранилищу при проверках отключены.
