# Подтверждение email и сброс пароля: исправления и выпуск

Причины по диагностике 8 октября 2026: API видел всех посетителей как bridge-IP 172.18.0.1; reset-confirm делил общий бюджет 2/мин; повторное письмо удаляло предыдущую ссылку; использованные записи удалялись через минуту; письмо сброса ставило точку сразу после URL. Отказы адресатам UniSender повторялись одинаковым способом до пяти раз.

## Поведение после исправления

- Повторный запрос письма подтверждения или email-сброса не удаляет ещё действующие ссылки. Их сроки прежние: 24 часа для подтверждения и 2 часа для email-сброса.
- Подтверждение email помечает выданные действующие ссылки использованными; повторное открытие до их истечения успешно и не меняет аккаунт повторно. Если администратор отозвал подтверждение, использованная ссылка не восстанавливает его.
- Успешный сброс атомарно использует все ранее выданные действующие ссылки этого пользователя и отзывает refresh-сессии. Другой или повторный запрос не может сменить пароль ещё раз. Конкурентные подтверждения сериализованы блокировкой пользователя, затем токена.
- Временные пароли администратора сохраняют прежний сценарий: повторный вход заменяет прежнюю временную ссылку; срок — 15 минут.
- Использованные записи подтверждения и сброса хранятся до своего expires_at. Очистка остаётся ограниченной пакетами по 1000 записей; индексы и таблицы уже есть. Миграция БД не требуется.
- В новом письме сброса ссылка стоит отдельной строкой без точки. API принимает одну конечную точку из старого письма: используемые URL-safe токены не содержат такую точку.
- API возвращает различимые `token_expired`, `token_already_used`, `invalid_token`, `weak_password`, `validation_error`. После удаления просроченного токена точную историю восстановить нельзя, поэтому неизвестная ссылка остаётся invalid_token.
- Страница подтверждения показывает отказ и форму повторного письма, а не молча возвращает на главную. Формы сброса и запроса письма учитывают Retry-After, показывают ожидание и блокируют преждевременные повторы. Временная и email-смена пароля получают подходящие сообщения.

## Лимиты

Прежние настройки AUTH_RESET_RL_LIMIT/WINDOW продолжают управлять запросом письма сброса. Для подтверждения добавлены отдельные настройки:

```dotenv
AUTH_RESET_CONFIRM_RL_LIMIT=5
AUTH_RESET_CONFIRM_RL_WINDOW_SEC=60
AUTH_RESET_CONFIRM_IP_RL_LIMIT=120
AUTH_RESET_CONFIRM_IP_RL_WINDOW_SEC=60
```

Первый бюджет относится к хешу конкретной ссылки, независимо от IP. Второй — защитный бюджет IP: он ограничивает перебор разных неизвестных ссылок. Это token bucket: лимит — ёмкость, окно — время восстановления полного бюджета. Если параметров нет, используются указанные значения по умолчанию. Старые Redis-ключи нового обработчика не используются и самостоятельно истекают; очищать Redis не нужно.

## Доверие к прокси

Образ API задаёт FORWARDED_ALLOW_IPS=127.0.0.1,172.18.0.1. Это соответствует фактически наблюдаемому Nginx → Docker bridge. Проверять нужно непосредственный адрес прокси; он может отличаться после изменения Docker-сети.

На сервере установите/проверьте значение в `.env`, если оно уже переопределено:

```dotenv
FORWARDED_ALLOW_IPS=127.0.0.1,172.18.0.1
```

Не задавайте слепое доверие `*`. В закреплённом Uvicorn 0.30.6 доверенные отправители перечисляются точными адресами. Nginx должен передавать клиентский IP в правильном API location, например:

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

Само наличие этой директивы в другом server/location не подтверждает настройку рабочего маршрута. Входящий API-порт должен сохранять существующую привязку к localhost. Количество API/Celery workers и параметры PostgreSQL данное исправление не требует менять.

## UniSender

Для invalid/permanent_unavailable/unsubscribed/temporary_unavailable/blocked/complained и других отказов адресату задача завершается отказом без быстрого повторения той же отправки. Временно подавленный адрес — не то же самое, что сетевой таймаут; ссылка истечёт раньше многодневной блокировки провайдера. При 429/5xx сервиса и сетевых ошибках прежние ограниченные повторы остаются.

В журнал попадают причина, обезличенный recipient_id, код провайдера и Error ID. Для принятой отправки записывается job_id. Полный ответ с email, тело письма, ключ и токен не логируются. Принятие письма не является подтверждением доставки. Саму блокировку/отписку или ошибочный адрес необходимо исправлять в данных/кабинете провайдера; эти списки автоматически не обходятся.

## Применение после обновления кода на сервере

Git-операции выполняются пользователем отдельно. После получения исправленного кода:

```bash
cd /opt/ni_site
docker compose build api worker beat
docker compose up -d --no-deps --force-recreate api worker beat
```

Пересоздание API/Celery выполняйте в техническое окно. PostgreSQL/Redis перезапускать не требуется. Beat использует тот же образ приложения, поэтому его сборка/перезапуск делает версию обслуживающих задач согласованной.

Соберите основной frontend и обновите статические файлы существующим способом из deploy.md. Если Node установлен на сервере и используется стандартная папка публикации проекта:

```bash
cd /opt/ni_site/frontend
npm ci
npm run build:app
```

Публикация dist в Nginx-root зависит от фактического пути на сервере; используйте действующий процесс публикации. Миграция Alembic для этих исправлений не нужна. Ранее удалённые ссылки/записи восстановить невозможно: для них потребуется новое письмо.

## Проверка после выпуска

1. По `docker compose top api worker` подтвердить прежние 6 API и 4 Celery processes, если эти значения используются на сервере. Они задаются текущим server compose.
2. Запустить обновлённый collect_peak_diagnostics.py. Ожидается reset_confirm_identity_is_literal_token=false, verify_request_deletes_previous_tokens=false, reset_request_deletes_previous_tokens=false, новое значение forwarded_allow_ips и новый отдельный лимит подтверждения.
3. У обычных внешних запросов API должен появиться клиентский адрес вместо общего bridge-IP. Проверки Docker/localhost по-прежнему могут приходить с внутренних адресов.
4. На тестовом аккаунте проверить две последовательно запрошенные ссылки; успешный сброс по одной делает остальные использованными. Для подтверждения email повторное открытие остаётся успешным до истечения срока.
5. В журнале искать `auth_link_rejected operation=... reason=...` и `auth_rate_limited scope=...`. Обновлённый диагностический скрипт агрегирует их. Для UniSender — один отказ на недоступный адрес вместо шести одинаковых попыток.

Сборщик из temporary передаётся на сервер отдельно, как и ранее; Git не переносит эту папку. Проверки, отправляющие настоящие письма, оператор запускает явно на собственном тестовом аккаунте.

## Проверки реализации

- Backend: 320 тестов прошли; два теста архива/MinIO пропущены из-за отсутствия локального эталонного архива и TEST_S3_* окружения. PostgreSQL/Redis для прогона — отдельные временные контейнеры, без использования рабочей БД.
- Frontend: 235 тестов прошли; TypeScript основного приложения и админки, обе production-сборки и prerender основного приложения завершены успешно.
- Проверены сохранение действующих ссылок при повторном письме, повторное подтверждение после очистки, параллельные подтверждения/сбросы, отзыв подтверждения администратором, разные пользователи одного IP, защита от смены неизвестных токенов, Retry-After, старый URL с точкой и маскирование данных почты.
- Реальный UniSender в тестах заменён MockTransport; письма пользователям не отправлялись. Диагностические скрипты сохраняют совместимость с прежними логами и дополнительно группируют новые причины отказов.
- `git diff --check` выполнен успешно. Локальные тестовые каталоги остаются исключёнными из Git существующей политикой .gitignore.
