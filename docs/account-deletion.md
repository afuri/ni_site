# Удаление аккаунтов

## Пользователь

В данных профиля (новый ЛК ученика и прежний ЛК учителя/ученика) доступны отправка
заявки с модальным подтверждением и отмена заявки. Пока заявку не исполнили,
аккаунт продолжает работать. Повторная отправка не создаёт дубль.

## Администратор

В разделе «Пользователи» есть удаление по ID и список заявок с пагинацией.
Перед удалением показываются ID, ФИО, логин, email, роль, количество попыток и связей.
Для подтверждения нужно повторно ввести ID. Удаление администраторов запрещено.
При обработке заявки сервер проверяет её ID: отменённая или заменённая заявка
не может быть исполнена из устаревшего окна.

Удаляются запись пользователя, сессии/токены, социальные привязки, связи сопровождения,
ручные упоминания учителя по ID, попытки, ответы, оценки, назначения олимпиад,
назначения уведомлений и заявки на школы/удаление. Удаляется связанная история
изменений и персональные записи аудита по actor/target user ID. Остаётся минимальный
аудит действия администратора с числовым ID удалённого аккаунта без ФИО/email.
Школы и общие материалы не удаляются: авторство заданий, олимпиад, пулов и публикаций
передаётся администратору, выполнившему удаление.

## Дипломы и надёжность очистки

В одной транзакции с удалением аккаунта создаётся запись `account_deletion_cleanup`:
ID пользователя и ID попыток. Затем очищаются файлы действующего формата:

- `attempt_<attempt_id>.jpg` в корне настроенного бакета;
- `certificates/teachers/<YYYY>_<YYYY>/certificate_<user_id>_<YYYY>_<YYYY>_<NN>.jpg` всех сезонов;
- предыдущие версии этих объектов и delete markers, если бакет версионируется.

Удаляется только точное совпадение ID. Нужны права S3 ListBucket, DeleteObject,
GetBucketVersioning; для версионируемого бакета также ListBucketVersions и DeleteObjectVersion.
Object Lock/retention может блокировать удаление: такая операция останется в очереди.

Если S3 недоступен, запись аккаунта уже удалена, но файлы **ещё могут быть доступны
по прежним прямым URL**. API возвращает `files_pending: true`, а админка показывает
очередь и кнопку повторной очистки. Запись очереди удаляется только после успеха.
Отказ части пакетного удаления не считается успехом; повтор идемпотентен.
Celery beat повторяет очистку каждые 5 минут (при работающем worker).

Резервные копии, локальные исходники дипломов, экспортированные CSV и скачанные
пользователями файлы эта функция не удаляет. Внешний CDN может сохранять кэш:
при его использовании нужно отдельно обеспечить инвалидирование. Не загружайте
заново дипломы удалённых аккаунтов из старых исходников.

## Развёртывание

1. Сделать резервную копию БД. Удаление необратимо через интерфейс.
2. Обновить код и собрать образы API/worker; применить `alembic upgrade head`
   из каталога backend/контейнера API: новая миграция `c9d8e7f6a5b4` создаёт только
   таблицы заявок и очереди. Миграция сама пользователей не удаляет.
3. Перезапустить API и worker, обновить сборки основного frontend и админки.
4. Для автоматических повторов запустить **один** процесс Celery beat, если его ещё нет:
   `celery -A app.core.celery_app.celery_app beat --loglevel=INFO` с тем же окружением,
   что у worker. Beat также выполняет уже настроенные maintenance-задачи проекта.
   Без beat немедленная попытка и ручной повтор в админке работают, автоматический — нет.
5. Проверить отправку/отмену заявки тестового аккаунта, затем удалить его с подтверждением.
   Убедиться, что очередь файлов пуста, вход невозможен, прежние URL документов недоступны.

Основные API: `/users/me/deletion-request` (GET/POST/DELETE),
`/admin/account-deletions/requests` (GET), `/admin/account-deletions/{id}` (GET/DELETE),
`/admin/account-deletions/cleanup` (GET), `/admin/account-deletions/{id}/cleanup` (POST).
